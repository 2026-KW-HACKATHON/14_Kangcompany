| | |

> **가상 페르소나다.** 공개자료와 프로젝트 방향을 바탕으로 만든 설정이며, 팀이 직접 한 인터뷰·설문 결과가 아니다. 실제 인물·가게를 재현하지 않는다.
> - `[근거]` 공개자료로 확인한 배경 (아래 출처 E1~E7)
> - `[가정]` 이름·나이·경험·목표·기기·숙련도·발화·인원·예산 등 디자인용 설정
> - `[설계 제안]` 페르소나에서 끌어낸 화면·문구·확인 항목 (효과가 검증됐다는 뜻은 아님)

> ⚠️ **선착순 확정과 다른 부분을 고쳐 두었다.** 원본은 "가게 수락 → **단체가 한 곳 선택** → 예약금 결제 → 확정" 흐름을 기준으로 썼지만, 팀 결정은 **가장 먼저 수락한 가게로 바로 확정(결제 대기)** 이다 ([IA 1장](ia/IA.md), [상태 정의도](ia/state-definitions.md)). 아래에서 ⚠️ 표시한 문장은 선착순 기준으로 바꾼 것이고, docx 원문은 괄호 안에 남겼다.

**이 문서에서 쓰는 흐름**: 요청 → 가게 수락(선착순, 결제 대기) → 예약금 결제 → 예약 확정 → 사전 주문·행사 → 영수증 확인·소비 기록. **가게 수락과 예약 확정은 다른 상태다.** 예약금 액수·환불 조건·변경 기한은 실제 제품 정책을 따른다.

## 1. 학생회 담당자 김서연

23세 · 광운대 학과 학생회장 `[가정]`

> "행사 장소를 잡는 것부터 회비 사용 내역을 설명하는 것까지 책임져야 하는 담당자."

- **상황** `[가정]` 개강총회 뒤 식사 모임. 참석 희망 20~30명, 수업 사이에 장소를 알아본다. 회비 사용 가능 금액을 총무와 먼저 확인하고, 학교 근처 가게를 찾는다.
- **목표** ① 인원·예산에 맞는 가게를 행사 전에 확정 ② 참석자에게 장소·시간·비용을 정확히 공지 ③ 행사 후 실제 지출과 영수증을 총무에게 전달
- **불편** ① 가게마다 같은 조건을 다시 설명하고 답변을 비교 ② 단체 채팅방 참가 응답과 가게에 전달한 인원이 달라짐 ③ 예약금·추가 주문·최종 결제 내역을 나중에 다시 맞춰야 함
- **디지털·환경** `[가정]` 메신저·지도·온라인 폼에 익숙. 이동 중엔 휴대폰, 행사 후엔 노트북으로 회계 정리. 기존 단체 채팅방과 함께 쓸 수 있어야 함
- **시나리오** ⚠️ 날짜·인원·1인 예산을 입력해 요청 → **고기굽는집이 가장 먼저 수락** → 총무와 집행 가능 여부 확인 후 예약금 결제 → '예약 확정' 확인 후 공지 → 행사 전 최종 인원·주문 점검 → 행사 후 사장님이 확인한 영수증 내역을 실제 결제와 대조 (원본 증빙은 별도 보관)
  _(원문: "가게의 수락 내용을 보고 고기굽는집을 선택한 뒤")_
- **근거와 가정의 경계** 광운대 법학부의 2026년 1·2학기 개강총회 개최는 확인 [E1]. 식당 뒤풀이·인원·예산·회계 부담은 가정
- **디자인 판단 질문** `[설계 제안]` 요청한 인원·예산, 현재 예약 상태, 다음 할 일을 **한 화면**에서 찾을 수 있는가? 예약금과 최종 지출을 혼동하지 않는가?

## 2. 동아리 담당자 이도윤

22세 · 광운대 밴드 동아리 총무 `[가정]`

> "공연 준비로 바쁜 와중에도 뒤풀이 시간과 인원, 회비를 맞춰야 하는 총무."

- **상황** `[가정]` 교내 공연 뒤 10~15명 식사. 공연 일정·장비 정리를 고려해 방문 시간을 정하고, 먼저 귀가하는 부원과 뒤풀이 참석자를 구분한다.
- **목표** ① 공연 후 이동 가능한 시간에 자리 확보 ② 확정 인원에 맞춰 기본 메뉴·예산 결정 ③ 현장 추가 주문까지 포함한 지출을 부원에게 설명
- **불편** ① 공연 참가 인원 ≠ 뒤풀이 참석 인원 ② 메뉴·수량 의견이 단체 채팅방에 흩어짐 ③ 장비 정리 중엔 통화하거나 예약 내용을 다시 찾기 어려움
- **디지털·환경** `[가정]` 메신저·간편결제·온라인 문서에 익숙. 연습실·공연장 대기 공간에서 휴대폰으로 **짧게** 확인. 숙련도는 높지만 집중할 시간이 부족
- **시나리오** ⚠️ 공연 종료·정리 시간을 고려해 날짜·방문 시간·예산 입력 → **월계치킨이 수락** → 예약금 결제로 확정 → 단체 채팅방에 참석 링크 공유해 인원 재확인 → 변경 가능 기한 안에서 주문 정리 → 행사 후 영수증 최종 금액과 비교
  _(원문: "월계치킨의 수락 조건을 확인하고 선택·예약금 결제를 거쳐")_
- **근거와 가정의 경계** 광운대 중앙동아리 48개, 밴드·연극 등 공연예술 동아리 확인 [E2]. 특정 동아리의 뒤풀이 빈도·인원·이용 실적은 미확인, 실존 동아리 설정을 빌리지 않음
- **디자인 판단 질문** `[설계 제안]` 짧은 확인만으로 방문 시간·최종 인원·주문 수량을 알 수 있는가? 예상 금액과 행사 후 실제 금액이 구분되는가?

## 3. 가게 사장님 박정호

59세 · 데모 가게 '고기굽는집' 운영자 `[가정]`

> "전화와 장부는 익숙하지만, 영업 중 새 예약 화면을 오래 들여다볼 여유는 없는 사장님."

- **상황** `[가정]` 저녁 영업 준비 중 학생회 단체 예약 요청을 받는다. 일반 손님 자리와 단체 자리를 함께 고려해야 하고, 인원·방문 시간·기본 주문이 정해져야 자리와 식재료 준비를 판단할 수 있다.
- **목표** ① 받을 수 있는 예약인지 **빠르게** 판단 ② 예약이 실제로 확정됐는지와 변경 내용을 놓치지 않기 ③ 영업 후 최소한의 입력으로 단체 이용 내역 남기기
- **불편** ① 전화받다가 날짜·인원·메뉴를 다시 묻거나 메모를 찾음 ② 자리를 비워뒀는데 취소·인원 감소를 늦게 알면 운영 부담 ③ **작은 글씨, 낯선 상태 이름, 여러 입력칸** 때문에 확인을 미룸
- **디지털·환경** `[가정]` 안드로이드 휴대폰으로 전화·카카오톡·사진 촬영은 혼자 함. 새 계정 설정·긴 양식·인식 결과 수정은 부담. **카운터에서 잠깐, 또는 주방 일을 멈춘 뒤 한 손으로** 조작. (요청받은 대상군에 맞춘 설정이며 연령에서 추정한 사실이 아님)
- **시나리오** ⚠️ 서연의 요청에서 날짜·인원·예산을 읽고 수용 가능 여부 판단 → 수락 (**이 시점은 '예약금 결제 대기'** 임을 확인) → '예약 확정' 상태와 최종 주문을 보고 준비 → 행사 후 영수증 촬영, 인식된 품목·합계를 실제 영수증과 비교해 수정·확정. 인식 오류 수정이 너무 길면 계속 쓰기 어렵다.
  _(원문: "'단체의 선택·예약금 결제 대기'임을 확인한다")_
- **근거와 가정의 경계** 전국 외식업체 214곳 조사: 전화 예약 95%, 노쇼 경험 65%, 예약금 설정 14% [E3]. 예약 운영의 배경이며 고기굽는집의 노쇼·손실·숙련도를 뜻하지 않음
- **디자인 판단 질문** `[설계 제안]` 설명 없이 **요청 수락과 예약 확정을 구별**할 수 있는가? 글씨를 확대해도 인원·시간·금액·버튼이 보이는가? 영수증 인식 오류를 스스로 수정할 수 있는가?

## 4. (선택) 주민모임 대표 최은영

52세 · 월계 생활권 생활체육 모임 총무 `[가정]`

> "운동 뒤 함께 식사할 사람만 모아, 가깝고 부담 없는 장소를 찾는 주민모임 담당자."

- **상황** `[가정]` 정기 운동과 별개인 친목 식사. 전체 회원이 아닌 참석 가능한 6~10명을 확인하고, 운동 장소·귀가 동선에서 벗어나지 않는 가게를 찾는다.
- **목표** ① 참석자만큼 자리 확보 ② 메뉴·비용을 미리 설명 ③ 기존 모임 채팅방을 유지하면서 예약 내용 공유
- **불편** ① 전체 회원 수 ≠ 실제 식사 인원 ② 가게에 자리가 있는지 다시 연락해야 함 ③ 회원마다 새 서비스 가입을 요청하면 참여 확인이 번거로움
- **디지털·환경** `[가정]` 카카오톡·지도·사진 공유에 익숙, 휴대폰 위주. 집이나 운동 후 휴식 중에 예약. **예약은 대표가 하고 회원에게는 필요한 정보만** 전달하고 싶음
- **시나리오** ⚠️ 채팅방에서 참석자를 정한 뒤 날짜·인원·예산 입력 → **광운분식이 수락** → 확정 절차 → 장소·시간을 채팅방에 공유 → 식사 후 영수증 기록으로 회비 사용 정리
  _(원문: "광운분식의 수락 조건을 확인해 선택하고")_
- **근거와 가정의 경계** 월계1동 주민 동아리 공간 지원, 주변 생활권의 정기 운동·친목 활동 사례 확인 [E4]. 인물·모임은 가상
- **디자인 판단 질문** `[설계 제안]` 학생회가 아닌 모임도 역할·예산을 자연스럽게 입력할 수 있는가? 대표가 기존 채팅방으로 정보를 전달하는 흐름을 지원하는가?
- 주민 페르소나는 지역의 일상적인 단체 수요를 보여주는 **선택 사례**다. 방학 매출 보완 효과나 주민 대상 확장 전략의 근거로 쓰지 않는다.

## 5. 디자인 기준 `[설계 제안]`

페르소나만으로 디자인 토큰의 적정성이 검증되지는 않는다. 아래 "확인할 상황"은 휴리스틱 평가·사용성 확인 때 그대로 쓴다.

| 항목 | 기준 | 확인할 상황 |
|---|---|---|
| 글씨 크기 | 본문 17px 출발. 큰 글씨 모드는 **20~22px** 정도부터 비교 (현재 토큰은 ×1.125 = 약 19px 유지, 휴리스틱 평가 때 ×1.25 = 약 21px와 비교하기로 10/4 결정). 시간·인원·금액·상태는 본문보다 먼저 눈에 들어오게 | 박정호가 휴대폰에서 요청 한 건을 읽고 설명할 수 있는지 |
| 글씨 확대 | 큰 글씨 모드 + 브라우저 **200% 확대**에서도 내용·기능 유지 [E7] | 예약 카드·수락 버튼·영수증 합계가 잘리거나 겹치지 않는지 |
| 주요 버튼 | 높이 48px 정도. **수락·취소를 붙여 두지 않고**, 색과 함께 글자로 행동 표시 | 박정호의 오조작, 이도윤의 짧은 확인 |
| 정보 순서 | **날짜·시간 → 인원 → 예산 → 예약 상태 → 다음 행동.** 가게에는 받을 수 있는 조건, 단체에는 진행 상황을 먼저 | 두 역할이 같은 예약을 같은 의미로 이해하는지 |
| 예약 상태 | '응답 대기 / 결제 대기 / 확정'처럼 구체적으로. 역할에 따라 다음 행동을 다르게 안내 | 가게 수락을 방문 확정으로 오해하지 않는지 |
| 금액 표시 | '예상 총액', '예약금', '행사 후 실제 결제액'을 구분 | 서연이 총무에게 금액을 정확히 설명하는지 |
| 영수증 | 사진 인식 → 확인·수정 → 확정. 확정 전엔 '확인 전' 상태 표시 | 사장님이 오류를 찾는지, 단체가 미확정 금액을 쓰지 않는지 |
| 말투 | 짧고 정중한 '해 주세요 / 확인할 수 있어요'. 행동·상태를 먼저, 유행어·과한 이모지 줄이기 | 역할이 바뀌어도 문구가 자연스러운지 |

### 화면 문구 예시

실제 상태·권한·변경 정책과 일치하는 화면에만 쓴다. 상태 이름은 [상태 정의도](ia/state-definitions.md)를 따른다.

| 화면·상태 | 문구 |
|---|---|
| 단체 · 첫 요청 화면 (G-01 빈 상태) | "아직 예약 요청이 없어요. 날짜·인원·예산을 입력해 가게에 요청해 주세요." |
| 단체 · 요청 전송 후 (G-03 응답 대기) ⚠️ | "가게의 답변을 기다리고 있어요. 가장 먼저 수락한 가게로 예약이 잡혀요." _(원문: "수락한 가게 중 한 곳을 선택해 주세요.")_ |
| 사장님 · 수락 직후 (S-05 결제 대기) ⚠️ | "요청을 수락했어요. 단체가 예약금을 결제하면 예약이 확정돼요." _(원문: "단체가 가게를 선택하고 예약금을 결제하면")_ |
| 단체 · 가게 수락 후 (G-06 결제 대기) ⚠️ | "고기굽는집이 수락했어요. 예약금을 결제하면 예약이 확정돼요." _(원문: "단체가 가게를 선택한 뒤 — 예약금 결제가 남아 있어요.")_ |
| 예약 확정 (G-06 / S-05) | "예약이 확정됐어요. 방문 시간과 인원, 주문 내용을 확인해 주세요." |
| 사장님 · 새 요청 없음 (S-02 빈 상태) | "새 예약 요청이 없어요. 요청이 들어오면 이곳에서 확인할 수 있어요." |
| 사장님 · 영수증 확인 (S-11) | "사진에서 읽은 내용이에요. 품목과 금액을 확인하고 틀린 부분을 수정해 주세요." |
| 단체 · 영수증 미확정 | "사장님이 영수증 내용을 확인하고 있어요. 확인이 끝나면 실제 소비 내역을 볼 수 있어요." |
| 단체 · 수락 없이 만료 (G-03 만료) ⚠️ | "기한 안에 수락한 가게가 없어요. 날짜·인원·예산을 바꿔 다시 요청해 보세요." _(원문: "아직 수락한 가게가 없어요. 날짜·인원·예산을 다시 확인해 주세요.")_ |

## 6. 데모 계정과 발표 시연

계정 종류·가게명은 업무요청 기준이며 `seed_demo.sql` 의 실제 계정 ID·단체명·메뉴·날짜와는 아직 대조하지 않았다. 페르소나 이름은 발표 설명용이다.

| 페르소나 | 연결할 계정 종류 | 시연 가게 | 시연에서 맡을 부분 |
|---|---|---|---|
| 김서연 | 학생회 계정 | 고기굽는집 | 요청 · 예약금 결제 · 행사 후 소비 확인 |
| 박정호 | 고기굽는집 사장님 계정 | 고기굽는집 | 같은 요청 수락 · 확정 확인 · 영수증 확인 |
| 이도윤 | 동아리 계정 | 월계치킨 | 공연 뒤풀이 시간·인원·사전 주문 확인 |
| 최은영 | 주민모임 계정 | 광운분식 | 소규모 모임의 요청·확정·기록 확인 |

**학생회 × 사장님 시연** (가정: 개강총회 뒤 식사, 행사일 D 18:30, 24명, 1인 25,000원, 상한 600,000원. 실제 데모 데이터·가게 조건을 우선해 조정)

1. **요청** — 서연: 날짜·인원·예산을 입력한 요청을 보낸다.
2. **수락** — 정호: 같은 조건을 확인하고 수락한다. 화면에 확정까지 남은 절차(단체 결제)가 보인다.
3. **확정** ⚠️ — 서연: 고기굽는집이 수락한 것을 확인하고 예약금을 결제한다. 양쪽에 같은 '예약 확정'이 보인다. _(원문: "고기굽는집을 선택하고 예약금을 결제한다")_
4. **행사 준비** — 양쪽: 최종 인원·사전 주문을 같은 내용으로 확인한다.
5. **행사 후** — 정호 → 서연: 정호가 영수증 인식 결과를 확인·확정하고, 서연이 실제 소비 기록을 확인한다. 예약금과 최종 결제가 중복 집계되지 않는지 점검.

- 발표에서는 가상 인물·시연 데이터임을 밝히고, 조율 시간 단축·노쇼 감소·매출 증가가 **관찰됐다는 표현은 쓰지 않는다**.
- 앱의 소비 기록은 회계 확인을 돕는 기록이다. 공식 증빙 요건 충족 여부는 별도 확인이 필요하며, 영수증 원본을 대체한다고 안내하지 않는다.

## 7. 현장 확인 항목 (가정을 고칠 때)

1. **학생회**: 최근 행사에서 장소를 어떻게 정했는지, 예약금을 누가 어떤 자금으로 냈는지, 영수증·회계 증빙 정리 방법
2. **동아리**: 공연 종료·정리·이동 시간을 정하는 방법, 식사 인원 확정 시점, 참석 링크가 기존 메신저 확인과 중복 업무인지
3. **사장님**: 실제 휴대폰으로 요청 수락·확정 확인·영수증 오류 수정을 수행하게 하고, 나이 대신 **읽기·조작·상태 이해·수정 부담**을 관찰
4. **주민모임**: 실제 식사 규모, 예약 담당 여부, 채팅방 사용 방식

특히 **사장님의 실제 수행 결과를 먼저** 확인해 글씨 크기와 예약 상태 문구를 조정한다.
